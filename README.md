# EventFlow

Основа backend: Python 3.12+, FastAPI, SQLAlchemy, psycopg и Alembic.
Реализованы подключение к PostgreSQL, первая миграция, health API,
регистрация, вход и проверка ролей. Управление мероприятиями и запись
участников — следующие этапы.

## Локальный запуск

Команды выполняются из корня репозитория. Нужны Python 3.12, uv и Docker Compose.

```sh
cp .env.example .env
# Замените пример пароля в POSTGRES_PASSWORD и DATABASE_URL в файле .env.
# Сгенерируйте JWT_SECRET и запишите в .env (не в git):
# python3 -c 'import secrets; print(secrets.token_hex(32))'
uv sync --locked
docker compose up -d --wait db
uv run alembic upgrade head
uv run uvicorn app.main:app --host 127.0.0.1 --port 8000 --reload
```

Не перезаписывайте уже существующий `.env`. Настоящие пароли не коммитятся.
Если порт 8000 занят, выберите другой через `--port`.

- `GET /health/live`: 200, если API работает; не проверяет БД.
- `GET /health/ready`: 200 при доступной БД, версии схемы `0001` и наличии
  всех пяти таблиц; иначе 503 без технических деталей ошибки.
- `/docs`: Swagger для проверки API.

Миграции запускаются явно до API; сервер не создаёт таблицы автоматически.
Данные PostgreSQL хранятся в Docker volume и переживают `docker compose down`.
`docker compose down -v` удаляет данные — для обычной остановки не используйте `-v`.
Изменение POSTGRES_PASSWORD не меняет пароль уже инициализированной базы.

Если схема ранее создана вручную через `db/001_initial.sql`, не выполняйте
`upgrade` поверх неё. После проверки полного соответствия исходной SQL-схеме
можно явно принять её под управление Alembic: `uv run alembic stamp 0001`.
Для новой базы всегда используйте `upgrade head`.

## Регистрация и вход

- `POST /auth/register` — JSON с `name`, `email`, `password`; ответ 201 с
  пользователем без пароля и хеша. Email уникален без учёта регистра; дубль — 409.
  Имя: 1–100 символов после проверки, пароль: 12–128 символов. Хеш: Argon2id.
  Поля `role`, `id` и любые другие лишние поля отклоняются с 422.
- `POST /auth/login` — форма `application/x-www-form-urlencoded`, поля
  `username` (email) и `password`. Ответ: `access_token`, `token_type: bearer`,
  `expires_in` в секундах. Неверные учётные данные — 401 с одинаковым сообщением.
- `GET /auth/me` — заголовок `Authorization: Bearer <access_token>`; возвращает
  текущего пользователя. Отсутствующий, поддельный или истёкший токен — 401.

В Swagger сначала выполните регистрацию, затем нажмите Authorize и введите
email в поле username и пароль. Swagger сам получает и подставляет bearer-токен.

JWT подписан HS256, содержит ID пользователя, срок действия, issuer и audience.
`JWT_SECRET` обязателен: случайное значение минимум 32 байта, без значения
по умолчанию. `ACCESS_TOKEN_MINUTES`: по умолчанию 30, допустимо 1–1440.
Смена секрета делает все старые токены недействительными. Отдельный logout,
refresh-токены и отзыв отдельного токена пока не реализованы.

Новый аккаунт всегда получает роль `participant`. Для назначения организатора
зарегистрируйте аккаунт и выполните доверенную локальную команду на сервере:

```sh
uv run python -m app.manage promote-organizer organizer@example.com
```

Публичного API назначения роли нет. Зависимость `Organizer` из `app.auth`
предназначена для будущих административных endpoints: 401 без авторизации,
403 для участника. Роль читается из БД при каждом запросе; роль из JWT не учитывается.
Таблица users уже есть в миграции 0001, новая миграция для авторизации не требуется.

## Проверки

```sh
uv run ruff check .
uv run pytest
# На отдельной тестовой БД после применения миграций:
TEST_DATABASE_URL="$DATABASE_URL" uv run pytest
```

Последняя команда предполагает, что DATABASE_URL экспортирован в текущем shell;
pytest сам не экспортирует содержимое `.env`. Без TEST_DATABASE_URL интеграционные
тесты явно пропускаются. Тесты авторизации используют транзакции с откатом,
но всё равно запускайте их только на отдельной тестовой БД.
SQL-тесты ограничений находятся в `db/tests/constraints.sql`.
Не запускайте разрушительные проверки downgrade на базе с нужными данными.

Описание схемы и обязательных транзакционных правил backend: [db/README.md](db/README.md).
Начальную SQL-миграцию после публикации нельзя редактировать: новые изменения
оформляются отдельными ревизиями Alembic. Autogenerate пока не настроен;
`uv run alembic revision -m "description"` создаёт ручную миграцию.
